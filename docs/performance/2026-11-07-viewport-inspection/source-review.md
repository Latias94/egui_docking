## Runtime semantics

`maybe_repaint` at `plugin.rs:161` continues requesting ROOT whenever any non-Settle request remains. It additionally requests only a non-root viewport currently named by `AwaitViewportTree`. It does not expand requests to inventory siblings, create a second queue, substitute cached output, increase transport deadlines or alter native output admission. The old initial one-shot `request_repaint_of` is removed from the New-phase branch because the same pending obligation is now handled uniformly at the end of the input hook and, while still pending, the output hook.

The private `request_frame(ctx, viewport)` sends the existing `RequestPaintWhileHidden` command to that exact viewport. ROOT submission in the TCP connection path is preserved explicitly. The pinned command's `requires_parent_repaint` returns true only for Close (`viewport.rs:1260`); this new target paint request does not implicitly broadcast to siblings or depend on a parent-propagation side effect. The explicit ROOT request remains responsible for inventory progress.

Freshness, error classification and callback ownership are unchanged:

- New truly absent IDs reply Unknown and leave the request vector before scheduling. Known IDs are the existing cached/raw-input union, not permanent authorization of a retired lifetime.
- The output hook refreshes and prunes the cache from the actual FullOutput before processing requests. A target absent there replies Removed and is removed before the final scheduler call.
- A pending tree request can reply only when `current_viewport == requested viewport`. The same output hook has just stored that viewport's current step, scale and tree; ROOT or the old cached child tree cannot satisfy it.
- Completion takes the FnOnce callback and removes the in-flight entry. Repeated paint scheduling does not duplicate callbacks or retain the completed request.
- Settle-only input still requests neither ROOT nor a selected target. Existing mixed-request and settle-limit behavior is retained.

`Context::send_viewport_cmd_to` is not a lookup-only API: it requests repaint and appends through state access that can insert a missing viewport (`context.rs:4921`, `:170`, `:759`). Removal safety therefore depends on the actual ordering, not merely on the original known-ID check. Input hooks run before the pass (`context.rs:1311`). During ROOT end-pass, an undeclared direct child's `used` remains false; repaint requests and command append do not declare it. Context removes it before building `viewport_output` (`:3597` onward). Only afterward do output hooks run (`:3295`). Inspection observes absence, completes Removed and stops requesting that target. The new real removal regression exercises this ordering and the later-output case that would expose resurrection.

The consumed-wake transition has a production counterpart. Pinned native output admission calls `ctx.acknowledge_repaint_request(viewport_id)` before application admission and can return Deferred without an egui pass (`host_seam.rs:2609–2614`). The Context acknowledgement resets the queued repaint delay without advancing pass numbers or producing a repaint (`context.rs:2456`). Repeating the pending selected-viewport obligation can therefore produce a new wake after that consumption. Whether the integration ultimately admits/render-paints the viewport remains its responsibility.

## Startup acknowledgement preserves the causal witness

Both new tests first perform a real ROOT declaration pass and a real child pass. The helper acknowledges a wake before each pass; each test also acknowledges the initial child repaint after that startup pass and only then installs its observed callback. This removes leftover startup/stabilization coalescing from the callback measurement. It does not service or satisfy the pending inspection request: that request has not yet been submitted.

The consumed-wake test still performs the full discriminating transition after submission:

1. A real ROOT pass starts the selected-child tree request, observes a child wake, and leaves the response channel empty despite an earlier cached child tree.
2. It acknowledges that child's wake without running any child UI. It clears the callback observations.
3. A later real ROOT pass must leave `cumulative_pass_nr_for(child)` unchanged while producing ROOT and selected-child wakes and hidden-paint commands. It must produce neither callback nor hidden-paint command for the unrelated child. The response must still be pending.
4. Only a subsequent actual selected-child pass can complete it, with the exact child ID, a step later than the most recent ROOT output, `Some(tree)` and the new child-only text.
5. The channel is then Disconnected, and another ROOT pass produces no request-owned child or unrelated wake.

No phase, cache entry, callback result or FullOutput is fabricated. Using the same acknowledgements as the integration isolates the real lost-obligation transition instead of turning a coalesced startup wake into a false failure. The correction strengthens the causal setup; it does not acknowledge away the child repaint that the later ROOT pass is required to re-arm.

The test creates a labeled WidgetInfo with `Role::Label`. In this pin, `Response::fill_accesskit_node_from_widget_info` writes that role's text with `builder.set_value(label)` and writes other roles with `set_label` (`response.rs:1022–1025`). The original final assertion queried the wrong property.

The final assertion still requires an actual node in the returned tree with the exact text `Fresh child tree`; it now checks `node.value()`. There is no relaxed label-or-value alternative, removed assertion, unconditional fallback, synthetic tree, role change, deadline increase or skipped response check. Earlier ROOT/child texts are different. Together with the pending-channel, child-ID and later-step assertions, this still rejects stale or unrelated output.

## Actual removal, unknown, unrelated and exactly-once coverage

The second registered test uses the installed plugin and real `Context::run_ui`, starts the same pending child request, consumes its wake without a child pass, then stops ROOT's selected-child declaration and removes the selected ID from raw inventory. The unrelated child remains declared.

The first actual removal output must omit the selected child, retain unrelated, and produce one typed Removed response followed by Disconnected. The test deliberately permits a target wake during that removal pass: its input hook ran before Context discovered the omission. It then clears observations and runs another real ROOT pass, requiring continued actual output absence and no selected callback. That later actual output catches a command mistakenly queued after removal which recreated the child state.

A new request for the retired ID must then return one typed Unknown response followed by Disconnected, without recreating its output or waking it. This also supplies an observable check that the stale plugin inventory no longer treats the removed ID as known. The absence oracle is the actual FullOutput; the test never reads through `ctx.viewport_for`, which would itself insert state. No ListViewports assertion is needed to establish this stronger subsequent Unknown behavior.

The new consumed-wake test explicitly checks no unrelated callback and no unrelated hidden-paint command. The removal test separately proves unrelated output survives the targeted removal. It does not claim that application-owned unrelated repaints are globally forbidden. The success, Removed and Unknown responses all assert channel disconnection after the single response, with post-completion no-rearm checks. These assertions retain the intended exactly-once evidence.
