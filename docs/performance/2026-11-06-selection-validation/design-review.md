**The priority findings concern the refactor’s correctness contract and repeated work. They are not claims of newly demonstrated runtime bugs.**

1. **P1 — A needs proof of the exact canonical base, rather than a general “Select is local” exemption.**

   Today the transaction path constructs an initial item ledger, applies the command, prunes vacant surfaces, canonicalizes the complete workspace, validates it again and reconciles its item ledger. Canonicalization itself performs structural input checks, traverses/rewrite-checks roots, computes reachability, performs two item-multiset scans and runs strict output validation. Together with the transaction’s initial and final scans, that is four explicit item-multiset constructions for a selection transaction. The explicit `candidate.validate()` immediately repeats the strict validator used by canonicalization’s successful output check. See [operation.rs:518](/Users/frankorz/codes/rust/egui_docking/crates/dockspace/src/operation.rs:518), [canonical.rs:204](/Users/frankorz/codes/rust/egui_docking/crates/dockspace/src/canonical.rs:204), [graph.rs:502](/Users/frankorz/codes/rust/egui_docking/crates/dockspace/src/graph.rs:502).

   The semantic obligations are necessary: exact item ownership, valid selected item, exact selected-first MRU permutation, canonical topology and valid presentations. Reconstructing every unchanged fact is avoidable when a private preparation path can establish that the base already satisfies those obligations and the edit changes only one selection and its MRU order.

   `WorkspaceIndex::build()` is **not sufficient evidence of complete canonical validity**. Its checks and fingerprint construction do not replace the whole workspace validator. A local-edit capability must originate from a verified publication/preparation path and remain bound to that exact immutable snapshot. Unknown or internally modified drafts retain the existing general path.
