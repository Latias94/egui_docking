# Dockspace and Dear ImGui: architecture and comparison boundary

Date: 2026-11-06. Reviewed dockspace source: `54840717a2454c957b13a667a939ddf8229e52e9`. Dear ImGui reference: `d88f238d1d363ef387382b2e29ad12cf96f826ac`, in `repo-ref/imgui`. This is a read-only source review. No build, test, benchmark, sampler, network operation, or repository modification was performed by this lane.

## Decision

**A bounded architecture refactor is justified. The strongest seam is between retained, compiled docking state and per-pass host presentation.** The current abstraction preserves useful renderer independence, but an unchanged surface still requires extensive metadata acquisition, program consumption, native widget registration, receiver rebinding, and proof production. A local selection can invalidate the entire surface compilation unit. These are implementation and interface choices, rather than unavoidable costs of using Rust or supporting another renderer.

ImGui provides useful evidence about retaining local state and delaying expensive gesture predicates. It is not evidence that replacing the core with mutable global pointers, removing validation, or rewriting only the arithmetic solver will close the product gap. Keep immutable output identity, historical-output rejection, and presentation settlement. Make the data protected by those identities cheaper to retain and consume.

The latest qualified 1,024-pane ratios are **6.48x idle, 11.56x two-frame click, and 15.03x resize**. They compare complete products. They are not docking-core ratios (`docs/performance/2026-11-06-linked-targets.md:45`).

## What the product benchmark actually requires

Both products render all 16/128/1,024 panes, with two tabs per pane, a balanced tree with alternating split axes, a 16,384-point height, scale 1, and a fixed 1/60-second clock. Both disable close buttons and render selected content text plus an 8x8 colored square. Idle and resize use one complete frame; click measures a real press and release, with real geometry-observation and hover preparation outside timing on both sides (`integration/product-comparison/README.md:50`, `:61`, `:75`).

The Rust timer includes `run_single_surface`, complete tessellation, and reporting the exact output receipt as Presented (`integration/egui-product-harness/examples/product_cost.rs:294`, `:317`, `:333`). The C++ timer includes `NewFrame`, `DockSpaceOverViewport`, every tab window's real `Begin`/`End`, `Render`, and CPU texture acknowledgement (`integration/product-comparison/imgui_product_cost.cpp:278`). Both stop with draw data live; counts, validation, and disposal follow. Neither side uses a GPU. Neither suppresses normal hidden-window preparation or repeat passes (`integration/product-comparison/README.md:80`, `:86`).

Native fonts, styling, interaction implementations, and output triangle counts differ. This prevents interpreting the product ratio as a single engine ratio, but does not weaken the evidence that this complete product is substantially slower at the tested task. All panes are visible, so hidden-pane clipping is not an explanation.

### Why the full product includes substantial bridge work

The selected pane path does more than render the supplied text and square. For every pane it registers an egui pane-body click/drag widget, creates a child Ui with a persistent salt, supplies a content rectangle/clip/layout, invokes the application, and then checks focus/content-widget registrations while the child is alive (`product_render/tabs.rs:34`, `:55`, `:64`, `:103`, `:123`). The benchmark calls only the normal application body; these per-pane scaffolding operations are product adapter policy. Native clipping, identity, layout and focus isolation are required outcomes; creating and disposing this particular object graph every pass is an implementation choice whose lower bound is unmeasured.

Every tab/splitter/control similarly creates native egui widget state and a core receiver association. At the next run the input bridge freezes the framework's complete prior widget state, then reconstructs whether native blockers permit a core hit against the exact presented output. `run_single_surface` also clones the ProductPointer draft before callbacks (`product_owned_run.rs:256`); its scene fields contain receiver vectors (`product_pointer.rs:78`). These costs must be attributed as **adapter interoperability and ownership work**, not uniformly called inherent framework overhead. Native egui widget creation is partly required by the current integration contract, while repeated binding vectors and full snapshot copying are candidate design costs.

ImGui's complete product is not devoid of counterpart work: it submits Begin/End for both tab windows, computes native hover/active ownership, and uses dock host windows, clipping, layout and native tab controls. Its docking core consumes those same retained window/widget facts directly. It does not bridge them through a separately versioned renderer-neutral output, receiver inventory and host input journal. A comparison against only its private layout/mutation code must exclude the Rust child Ui, native widget submission, pointer freeze, and proof work from the matching kernel, then report those bridge costs separately. A complete-product comparison should keep all of them and label the ratio accordingly.

## Required behavior, conditional costs, and avoidable design work

The product contract requires every visible pane and both tabs, current label geometry, real click/selection behavior, ordinary native hover/focus/occlusion rules, selected content callbacks, and complete CPU draw data. It also requires current output identity on the Rust side because that is its public product path. The library's own correctness contract requires stale-output rejection, multi-pass consistency, and refusing input against an unpresented candidate. Do not remove these to improve the result.

Dockspace also supports per-pane minima, general constraints, multi-surface/native transitions, atomic splitter junctions, touch/magnetic targeting, detailed semantic actions, and historical outputs. Some have no matching ImGui contract. They should be tested separately when active; their existence does not justify paying every derivation or proof cost in a one-surface, ordinary mouse, no-gesture idle frame. In this benchmark no drag/drop is in progress, so drag previews and active resize constraints are not a measured functional requirement, while correct future gesture admission remains one.

The clearest avoidable work is the **shape of the internal protocol**: inspecting a complete program to find titles; rebuilding pass-owned resource maps despite unchanged metadata; resolving records already delivered by the current plan back through semantic identities; invoking DropTarget visitor steps with an empty egui consumer; compiling a whole surface after a local selection; and reconstructing proof of renderer output ownership through descriptors rather than an ownership fact emitted by the renderer. The first five are source-visible. The last is a deeper integration hypothesis, since arbitrary pane callbacks can mutate egui state and the existing audited fork already addresses part of that problem.

## Three refactor priorities

### 1. Separate retained scene structure from local semantic and output generations

**Evidence: strong for scope amplification; incomplete for the fraction removable without changing semantics.** The matching Ready path shares an immutable plan. Local tab edits make that path unavailable before preparation, then `compile_surface_plan(...).finalize()` produces a new complete surface (`surface_contribution.rs:334`, `:362`). Installing it compiles the hit manifest, links the program, and compiles semantic output (`scene/lifecycle.rs:1264`). In contrast, ImGui queues focus into an existing tab bar and retains node/window geometry.

The latest archived renderer-free full update supports investigating this seam: 1,024-pane idle process p50s are 1.633-1.655 ms while semantic selection is 9.645-9.875 ms (`docs/performance/2026-11-06-linked-targets.md:61`). That workload includes an owned recording sink and complete output commit; it is not a pure reducer timer. Root's new current-548 click sampling finds substantial compiler/validator presence and only 0.80% numeric-layout presence. These observations support a broad invalidation/output problem over a numeric-layout-first diagnosis, without establishing additive phase times.

Use a deeper retained-scene module that privately owns topology/layout/chrome dependencies and prelinked execution records. Let selection update the affected tab group/content slot and the relevant source semantics. Mint fresh output and input authority separately from unchanged geometric storage. When the newly selected item has a different minimum or tab policy, propagate that dependency to the affected layout and scene records. This preserves the public renderer-neutral API and historical outputs; it need not expose a public cache or turn outputs into mutable pointers.

Falsifier/acceptance: with fixed equal metadata, changing one tab should not rederive unrelated pane geometry, targets, and semantic records. With a different minimum/policy, normalized output must exactly match a complete rebuild. Old and in-flight outputs must retain their own semantics and be rejected/settled exactly as today. An experiment must show product and complete-update improvement, rather than only a smaller private kernel.

### 2. Give pane metadata and native text resources a persistent validity boundary

**Evidence: strong for the interface restriction and repeated acquisition; medium for the achievable end-to-end saving.** `PaneView::title` explicitly states that a later pass reads the title again (`pane.rs:23`). `minimum_size` similarly returns a current value without a revision (`:105`). Normal passes measure even when an initial Ready plan exists (`product_owned_run.rs:382`). PaintResources is created anew, and shaping owns another title String (`measurement.rs:276`). Prior same-pass resource sharing is already present and should be retained.

Introduce an optional stable metadata publication/version, owned at the adapter boundary, with a dynamic fallback preserving the existing trait behavior. It must cover title/rich-text identity, per-item minimum size, item availability, font/style/scale changes, and other measurement-dependent inputs. A deeper metadata module should own the cache and invalidation facts; do not spread fingerprints and cache keys through callers. A title changing during content callbacks must remain observable at the documented next-pass boundary.

This optional cross-frame API is separate from the nearer-term full-Q row-batch experiment. The row batch must still invoke the resolver for every current requested value, retain all callbacks and unavailable answers, and preserve variant/value validation and stable error order. It removes keyed materialization and repeated association/set proofs; it supplies no stability promise and does not authorize skipping callbacks.

This is not a claim that ImGui never measures text: `TabItemEx` still calls `TabItemCalcSize` each frame. The useful comparison is that it consumes retained window/tab state directly and does not need a renderer-neutral measurement answer object and per-pass resource roster for every stable tab.

Root's fresh 548 sampling places measurement/resources at 11.47% inclusive in idle and 23.75% in click, with overlapping categories and preparation/disposal included. Treat that as corroboration for a controlled experiment, not a claim that exactly that percentage can be removed. Test stable metadata, a one-title update, changing selected minima, font/scale update, missing-item recovery, and repeat-pass invalidation with the same complete outputs.

### 3. Make the host boundary consume linked native records and renderer ownership facts

**Evidence: strong for redundant adapter consumption/joins; medium for replacing proof scans; unknown for the final combined saving.** The latest patch already removes semantic lookup for DropTarget execution. It does not remove those steps, extend linking to pane/tab/splitter records, or avoid repeated native widget and receiver-vector transport. Current `receiver_for_*` paths still resolve IDs through the hit manifest. The egui consumer ignores DropTarget steps, while `interact_receiver` creates native responses, optionally cancels native drag ownership, and records bindings for later journal admission (`product_render/mod.rs:234`).

A deeper host-delivery module should own one compiled record-to-receiver association and the native widget facts needed for the current output. The current-plan fast path can borrow a prelinked receiver slot; arbitrary/foreign record wrappers must retain their current validation behavior. An official adapter should receive a paint stream of actual visual/native-control operations plus a separate retained query service for dormant docking targets. Preserve a whole-program completion obligation internally without requiring every renderer to visit inert interaction-only records. This generalizes the current successful binding change without repeating its solved lookup optimization.

Include input freeze in this prototype's accounting: retain a framework-owned immutable completed-pass snapshot or token, instead of copying the full widget inventory into the bridge, if the framework can provide that lifetime. Keep the snapshot fixed before callbacks and shared across repeat passes. Unknown interactive widgets, overlays/modals, transformed layers, and stale output bindings must still block exactly as today. Whether a no-input idle run can omit any snapshot work also depends on continuation/focus behavior; the current unconditional capture is a hypothesis to test, not permission to skip input invariants.

The output half of the same seam is also worth a bounded prototype: framework-owned append/mutation facts or sealed output spans may prove exact ownership more directly than rebuilding/comparing descriptors. The specific candidate reduction is capture/materialization and scanning/comparison of unchanged prior shape descriptors and layer prefixes; framework-issued mutation/append facts would have to preserve those same final-output guarantees after hooks. Run every pane callback and preserve its full content output. Existing callbacks have access to a general egui context, so an ordinary wrapper alone cannot prove that earlier shapes, transforms, other layers, or output hooks were untouched. Keep the current check until a renderer-owned mechanism proves the same cases. Existing fork paint-audit improvements are already part of the baseline.

Root's fresh idle sampling includes receiver queries 7.72%, create_widget 9.84%, get_response 2.83%, child UI 4.60%, and an output_proof subtree at 15.665%. Categories overlap and include unmeasured preparation/disposal. The last figure is an inclusive subtree containing actual pane content: idle sample lines 43-46 show PaneView::ui and native Label work underneath PaintAudit::check_append. It is neither the audit's exclusive cost nor a deletable audit budget. Exclusive audit CPU cost has not been measured. These samples support inspecting the boundary; they do not prove all native widget work is redundant, quantify avoidable capture/scanning, or establish that output verification is dispensable.

## Fair renderer-free docking experiments

### First: extend the existing real layout extraction, with equal output ownership

The existing probe already includes unmodified pinned `imgui.cpp` and calls the actual private `DockNodeTreeUpdatePosSize`. It compares all 2N-1 rectangles in an integral, unconstrained common subset (`integration/product-comparison/layout.md:7`, `:32`). Its old `d6dc6d7` report measured approximately 556/325/7 microseconds for full Rust projection/prepared Rust projection/ImGui in-place update, respectively. Those are old boundaries and source, not current-548 measurements (`docs/performance/2026-11-06-layout-kernel-results.md:3`).

Add distinct current-source conditions, rather than relabeling that result:

1. Actual ImGui in-place geometry update, as today.
2. The same actual update **plus export of every normalized node rectangle** into a pre-sized flat owned buffer; separately report export allocation if fresh allocation is required.
3. Current full Rust measurement/projection and its complete preserved output, as the reference.
4. A private current Rust reusable topology/scratch representation that still exports the same complete immutable result; all constraint/split metadata required by Rust callers must remain present, or be explicitly listed as unmatched output.

Match dimensions, split ratios, separator, visibility, inactive minima/maxima, and integer rounding. Verify every rectangle/count/digest after timing. Keep fresh immutable export and reused output-buffer cases separate for both sides. Measure allocation requests and retained bytes separately from CPU. This tests data structure/ownership choices without pretending ImGui implements the general constraint contract. Expected harness cost is low because the extraction and oracle already exist; production refactor cost remains to be measured.

### Second: actual docking mutations plus normalized retained state

For topology operations, the real private entry points are `DockContextProcessDock` (`imgui.cpp:18697`), `DockContextProcessUndockWindow` (`:18858`), `DockContextProcessUndockNode` (`:18874`), and the real tree split/merge/layout functions. Build and warm real ImGui windows/nodes outside timing. Use these handlers with actual DockRequest structures, then run the necessary production finalization before observing state. DockContextProcessDock itself only writes NextSelectedTabId at `:18829`; stopping there does not establish final selected/visible state.

Start with a **command-level** workload: idle retained snapshot, resize, move one tab to an existing group, split-dock a tab, and merge/remove the empty source. Feed matching validated semantic commands to dockspace. Report command admission, mutation/finalization, and normalized export as distinct conditions, plus a complete command-to-export condition. Both sides must produce the same normalized tree, axis/ratio/common-subset rectangles, ordered tab identities, selected/visible item, and item-to-group assignment. Stable IDs can be normalized, but no operation or changed output may disappear. Check all unaffected panes as well as the edited group. Construct/reset state outside both timers or include it on both sides.

Do not add a selection field assignment to this table and call it a click. Actual selection goes through `TabBarQueueFocus`, `TabBarLayout`, native interaction, visibility, and focus. The private TabBarLayout is defined inside `imgui_widgets.cpp`; it interleaves context, text metrics, width allocation, scrolling and native controls. A local include/wrapper around that implementation can expose it, but freezing its inputs narrows the experiment to tab-state/layout, and leaving draw-list calls in means it is still not fully renderer-free. This needs an explicit label and preservation test.

This command experiment is moderate work and useful for mutation locality. It does not measure mouse arbitration, preview policy, real drag delivery, presentation acknowledgement, or historical outputs. Keep those in the complete product and dockspace contract workloads. Do not compare it against `frame_cost` unchanged: that example records every geometry/receiver record, confirms the entire program, commits an owned output, and separately settles it (`integration/dockspace-host-harness/examples/frame_cost.rs:173`, `:408`). Add an equivalent normalized-export sink boundary for both implementations and keep the existing complete recording/settlement measurement visible.

The command benchmark's timed Rust boundary must exclude egui child Ui creation, `Ui::interact`, ProductPointerInputSnapshot capture and reconciliation, and output descriptor auditing. Those paths have no counterpart in the private ImGui command/layout boundary. Record them as separately scoped bridge experiments: (a) native docking control submission and complete selected-pane child UI/content, (b) completed-pass snapshot capture plus one real pointer delivery with blocker/overlay cases, and (c) complete output proof/receipt generation. Never subtract these measurements from independently sampled product totals to claim an exact residual; compare each experiment's before/after variants and preserve the complete product as the final check.

### Third, only if needed: preserve full docking decisions while suppressing drawing

A full renderer-free interactive ImGui docking subsystem is not available as a single callable upstream module. `DockNodeUpdate` combines root housekeeping, actual layout, splitters, tab submission, drag targets, drawing and child recursion (`imgui.cpp:19427`). Generic `ItemAdd`, `ButtonBehavior`, focus, window ordering and hover arbitration participate in the result. Simply disabling Render/tessellation leaves much widget/draw-list generation in place; disabling ItemAdd/TabItemEx changes decisions.

The honest experiment would create a temporary instrumented ImGui adapter/sink that retains all input registration and decision paths, substitutes recording hooks only for draw emission, and emits a normalized ordered docking/control/content inventory. It must be validated against the unmodified pinned product across idle, real two-frame click, resize, tab drag, edge/center drop, overlay blockers, and focus/scroll cases. Both products must preserve the same declared output inventory, including hit regions and order when those are in scope. The exact modified source and any unmatched constraints/presentation features must be recorded.

This is a higher-cost extraction with maintenance risk: the relevant logic is woven through imgui.cpp and imgui_widgets.cpp, not isolated in DockNode. Do not prioritize it over a current-source layout/export probe, command/state experiment, or the product-boundary refactor. It can answer a genuine question later, but creating a second incomplete docking engine or proving equivalence with an elaborate script would be a poor trade.

## Recommended implementation direction and unresolved claims

Prefer the retained-scene/host boundary refactor over a wholesale ImGui-style rewrite. Keep a small number of explicit dependencies: topology/layout facts, selected/group state, metadata/style facts, interaction state, and output generation. Internally retain or share prevalidated geometry/relations; let each host bind the current generation and submit required native controls. The boundary should hide receiver linking, validity, query preparation, and resource ownership from callers. It should make unchanged work naturally reusable rather than exposing another collection of stamps, fingerprints, and caller-maintained caches.

A dense/reusable layout kernel remains a sensible subordinate change. The older layout result proves an opportunity in a common subset, while current click sampling indicates that the arithmetic solver is not the dominant live problem. It should not be the first large rewrite or be sold as a solution to a 6-15x complete-product gap.

What is not yet established: the exact milliseconds attributable to each design issue; how much the same invariants permit local scene patching; whether renderer-owned output proof can replace the current audited descriptor path; how much native egui control/text/tessellation work remains after core improvements; and the minimum fair ImGui renderer-free interaction boundary. Root's 548 sampling is attribution evidence, not a clean timed phase partition: inclusive categories overlap, initialization/warmups/click preparation/disposal are present, and inlining can hide work. No percentage is added to another here.

The next decisive result should be a controlled prototype that keeps complete output and input obligations, reduces unrelated work after one selected-tab change, and moves both complete headless update and actual product timing. Reject a prototype that wins only by dropping targets, native blocker arbitration, content callbacks, output settlement, or validation at a required external boundary.

## Cross-review challenges

The state and scene lane drafts were read after this lane's first draft. They agree on local-selection scope amplification, the redundant synchronous keyed-answer protocol, ordinary receiver joins, and preserving real geometry/authority checks. Three qualifications should control the combined recommendation:

1. **Do not rank idle deep equality as the main explanation of the gap.** It is a high-confidence bounded cleanup and may make a good first experiment. Root's added scene_value_comparison classification measures SurfaceSceneSet::eq inclusive at 4.288% in idle and 2.887% in click. The earlier approximately 1-2% observation refers only to HitGeometry/LayoutFacts leaf categories, not complete scene equality. The broader classification strengthens evidence for a measurable equality cleanup but still does not establish it as the main root cause. The scene draft's first-ranked equality item should be read as confidence/scope, not expected latency impact. Inclusive percentages overlap other categories and are not additive phase budgets.
2. **The proposed generation must remove a protocol, not rename SurfacePlanScene.** The current type already co-owns plan, hit manifest, semantic manifest and paint-program link in Arc-backed immutable state. Another owner containing those same values, followed by the same full-Q maps, validation joins, whole-surface rebuild, semantic relookup and deep comparisons, would not resolve the diagnosis. State concrete deletions: row-fill once instead of keyed self-validation, retain actual unaffected structural inventory across selection, execute linked roles without a semantic rejoin, and compare binding facts/identities instead of known-shared immutable bodies. Any additional storage owner needs an explicit purpose among these deletions.
3. **The output_proof subtree is not an audit-only CPU measurement.** Its 15.665% inclusive idle share includes PaneView::ui, Label and other actual callback work (sample lines 43-46); audit-exclusive cost and removable capture/scan cost remain unmeasured. It cannot be compared with a receiver category to rank removable milliseconds. For the present general callback contract, final-hook and cross-layer mutation detection are real obligations. Row joins and empty DropTarget visitor consumption are directly redundant for the current adapter path; full widget registration, child Ui isolation, and output proof are partly functional mechanisms. Improve their ownership boundary only with equal behavior and retain every callback. The concrete output-seam hypothesis is reducing prior-descriptor/layer-prefix capture and comparison through renderer-owned facts, not bypassing content or counting its cost as auditing. The native snapshot/receiver bridge is a more concrete architecture candidate than claiming a free audit bypass.

A practical order for a future implementation is the private synchronous full-Q row-answer path plus ordinary receiver links, then a deliberately narrow equal-metadata local-selection inventory reuse. Full-Q row answers preserve the complete current request set and all resolver callbacks; they only remove redundant representation and association work. Cross-frame metadata publication is a separate optional API that could provide an explicit stability promise later, with a dynamic fallback. Renderer-owned input/output facts are another independent seam with broader integration cost. Neither is a prerequisite or an assumed callback reduction for the first core improvement. This round is analysis only; no implementation is requested by this lane.
