The sufficiency argument covers both callers:

- remove_item returns `!items.is_empty()` only after the original node/type/item checks, visual removal, MRU lookup/removal and selected repair all succeed. A missing MRU entry still returns the same error before any bool is returned. The new value means source Tabs has an actual remaining item, not merely “the command changed something.”
- detach_payload's Item arm calls cleanup immediately. Source validation already established exact generational root membership before this exclusive mutation. No detach, root replacement or second removal occurs between the actual remaining-items result and cleanup.
- prepare_content_close validates its frozen Item source before removal. Optional select_tabs_item changes only selected and MRU (`1698–1714`), so the items-derived fact is still true/false afterward. Its errors are still observed before cleanup; it never removes a second item.
- cleanup preserves the original root lookup and MissingRoot error before consulting the bool. With a central root, it retains the original no-retirement behavior. With a noncentral root and source_has_items=true, the source's remaining item proves that root is nonempty. With source_has_items=false, the original whole-root DFS and removal path run unchanged; empty source does not imply empty root.

| Current situation | Required cleanup behavior, preserved by the patch |
| --- | --- |
| Source still has an item | Keep root without the redundant existence walk |
| Source empty, another branch has an item | Original DFS says keep; later normalization repairs the empty source |

| Empty or nonempty central root | Preserve root under the original central rule |

Priority 2, defer until the first result: borrow current child rosters while refreshing placements.

`graph/authority.rs:282–292` clones an entire children Vec only to iterate its copied NodeIds while updating a separate placements map. Node storage and placements are disjoint fields, so the current children can be borrowed while mutating only the placement map. This can remove the temporary roster allocation/copy without changing Node ownership or payload storage. Use one concrete private implementation, not a new provider/container. Preserve each full generational key's existence check, placement equality check, root/parent/index values and the current skip behavior for missing children.

A crucial cost boundary is to keep Arc::make_mut lazy: if all child placements already agree, an implementation must not eagerly detach the whole SparseSecondaryMap. The existing place_node comparison avoids that COW. It is especially relevant to repeated refreshes: wrap_target_branch refreshes its wrapper at operation.rs:3472, while finish_item_move's output_splits refresh it again at canonical.rs:327–328. In a nonempty-source inner wrapper insertion, nothing rewrites that wrapper between these calls. Both currently clone its two-child roster, even though the second generally finds equal placements. Removing just the temporary Vec is safer than deleting one refresh globally; source collapse/flattening can change direct children between earlier and final frontier work.

The cheapest next location check is to inspect this exact frame below current timed edge prepare using the already saved sample/disassembly if needed. No whole-repo audit or new profiler is required to prove that children.clone exists; a sample absence would not quantify it as zero. Keep semantic_edits_share_placements_and_discarded_structure_edits_detach_them plus the existing local Item/ABA/placement witnesses. Expected physical deletion is one temporary Vec per refresh; complete benefit remains unknown. This does not remove the structural placement-map COW required by a real edit.

Priority 3, only with allocation/callsite support: avoid target Tabs clone-then-grow.

For a cross-pane center/gap transfer, `insert_items` at operation.rs:3250–3288 first gets the target mutably. NodeStore::get_mut invokes Arc::make_mut; Node::clone copies the two complete owned Vecs (`graph.rs:197–205`). It then immediately inserts one visual item and one MRU entry. The formal target begins with two items. The locally installed Rust 1.95 alloc source shows Vec::clone delegates to slice::to_vec_in (`alloc/src/vec/mod.rs:3746–3750`), whose trivial-copy path requests capacity equal to length (`alloc/src/slice.rs:444–455`). Consequently the target's first COW clone does not reserve for the known insertion, and both vectors request growth on their following insertion. A reallocator may extend in place; an additional physical copy of all old elements is not guaranteed. Source alone establishes the capacity/growth pattern, not allocator time.

A bounded follow-up could let the existing insertion owner construct the shared target's two fresh vectors with room for that actual insertion, copy existing values once, then run the same insert/MRU semantics. Retain the SlotMap allocator and generational keys, original workspace/old Node payload, unique-followup behavior and exact selected/visual/MRU order. Do not globally inflate all Node::clone capacities: source deletion/selection and other writers would pay for space they do not need. Do not adopt a persistent NodeStore or a hand-written small container. Keep logical clone/copy accounting honest if the construction route changes.

The cheapest useful verification is one untimed observation of target items/MRU length, capacity and shared/unique status immediately around first COW and insertion, outside the immutable formal probe; alternatively use the saved allocator callsite under the exact insert owner. Root would have to provide that observation; none was run here. The existing center_move_copies_only_two_complete_tabs_payloads_and_unique_followup_copies_none, discarded-prepared-candidate, old-ref and all tab-MRU tests are more meaningful than a mirror test of a reserve value. Complexity/ABI/fallback risk is higher than the first two candidates, and no macro benefit is promised.

Local root finish has small repeated reads but no new proven large deletion.

Actual edge edits still rebuild O(N) root rows, five root-local arrays, sorted identity directory and split payload Arc handles (`root_structure.rs:115–220`). The current profile's complete_item_move_structure reserve observation makes that a real location to investigate, but does not prove these required fresh structural results can be omitted. The transient split_rows list is populated during traversal then cleared/rebuilt in identity order; replacing its temporary counting use with a local scalar could delete writes, but not the final sorted directory. That is a small source fact, not a reason to introduce a second builder, speculative dirty cache or old-output mutation. Precise saved-callsite attribution is needed before another reserve change, because five result arrays plus the pending stack can allocate. The existing oldN+2 capacity hint and rows-only completion must be retained unless a separately reviewed experiment changes them.

Owned export is already a linear complete join and is not a supported deletion target here.

NodeMap owns fresh values and immutable exact topology. iter_preorder (`layout/projection.rs:69–83`) is a borrow-only zip and allocates no traversal state. The formal export (`docking_cost.rs:277–350`) joins each projected identity with actual live graph data, writes the complete owned word Vec, verifies exact preorder and includes every item/selection/rectangle. Tabs rows deliberately keep only identities; storing current items/MRU/selected into a retained topology to avoid the graph read would create stale semantic data and could weaken old-output independence. Caching/reusing that word buffer or returning a lazy facade violates the requested fresh owned output. The probe's capacity, traversal, assertions, timer and complete export are frozen and were not changed. No second keyed-map walk remains to eliminate from that export.

The independently cloned NodeStore slot/handle inventory, fresh issuance after a real root edit, and one owned outcome/report are architectural costs that cannot simply be removed by mutating the original and undoing it on failure. Prepared candidates can be discarded or retained alongside old refs/outputs. A rollback log, weak lifetime shortcut or skipped MRU permutation would be a different and unjustified contract. Persistent NodeStore had broad adverse evidence and is not recommended again. Neither rejected checked-weight propagation nor binary initialization is relevant to these new command findings.
